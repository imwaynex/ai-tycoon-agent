# D16 live code｜操作流暢度 friction note

> 給 McQueen／GPT-6 High。只看操作流暢度，不改主流程：**任命 → 出征 → 戰報 → 再派／撤回**。遵守 D14：L0 正文 ≤2 行、NL 不在首屏、`cancel=false`、折返 L0 必帶原因。

## Code 對診：具體摩擦

1. **「去出征」其實只是導航，接著還要再按「派出」**
   - **觀察**：`App.tsx:180-187` 的任命席 `去出征` 只呼叫 `go('dispatch')`；到 `App.tsx:217-229` 才選期間並按 `派出`。`copy.ts:22-25` 也把兩者做成兩個 CTA。
   - **推定摩擦**：使用者可能把「去出征」理解成已準備出發，抵達後又看到一次派出，形成「重複確認／多一步」的卡感。

2. **期間選擇與派出之間缺少清楚的選定回饋**
   - **觀察**：`PeriodPicker` 在 `App.tsx:432-449` 只以 `.seg.on`（`styles.css:120-126`）呈現選中；`onPick` 直接呼叫 `setTimeWindow`（`App.tsx:219`），沒有 inline「已選 X 秒」或 CTA 伴隨變化。
   - **推定摩擦**：三段期間的節奏是「掃描 → 點選 → 再確認」，但選擇後使用者仍要自己記住期間，才敢按通用文案「派出」。

3. **步驟列可任意跳席，像 Tab 而非目前任務的進度**
   - **觀察**：`STEP_KEYS` 的三個按鈕在 `App.tsx:141-145` 無條件可點；`go()`（`App.tsx:88-92`）只換 screen、關閉展開層，沒有狀態／可達性判斷。`履歷` 又是同一列右側入口（`App.tsx:151-155`）。
   - **推定摩擦**：可在尚無戰報時跳到戰報、在出征中跳回任命；使用者被迫自行判斷「現在該回哪一席」，主路徑被上下文切斷。履歷離開後也沒有明確的回上一席動作，只能再找步驟列。

4. **歸來到再派有兩個入口，且同一動作使用不同文案**
   - **觀察**：戰報主 CTA `再派` 在 `App.tsx:283-285` 執行 `redispatch()` 並進 `dispatch`；但任命席在 returned 狀態，`App.tsx:181-185` 的 `去出征` 也會偷偷執行 `redispatch()`，不是單純導航。`store.ts:171-175` 會新建 ready 契約。
   - **推定摩擦**：同一個「建立下一趟」動作散落兩處，使用者在任命席按「去出征」時不易預期狀態已改變；戰報→出征也沒有說明期間沿用上一約、或「下一趟已準備」。

5. **派出成功與自動歸來都沒有中間回饋，畫面可能直接跳**
   - **觀察**：`act()`（`App.tsx:94-103`）只有錯誤時設 `error`；ready 狀態按 `派出`（`App.tsx:226-228`）沒有成功 toast／過渡，依 state 更新直接變成 in-field。計時器到期時（`App.tsx:106-120`）同時 `settle()` 和 `go('report')`。
   - **推定摩擦**：使用者無法立即確認「已派出」或「正在結算」；若正看別的席位，計時器會把 screen 強制拉到戰報，形成突兀的 context switch。

6. **切席會清掉調整層，且操作中的輸入沒有保留保證**
   - **觀察**：`go()`（`App.tsx:88-92`）每次切席都 `setAdjustOpen(false); setNlOpen(false)`；NL sheet 的文字狀態是元件內 local state（`App.tsx:383-389`）。
   - **推定摩擦**：使用者為確認上一趟結果而切去別席，再回戰報時調整層已收起；若尚未確認 NL，切席會卸載輸入區，造成「我剛剛的操作去哪了」的不確定感。這是切換／回饋摩擦，不涉及把 NL 提到首屏。

## IA change options

### A｜保守順路（建議先試）
- 不動狀態機、主流程、D14 CTA 文案；`去出征` 仍只做導航，`派出` 仍是唯一實際出征 commit。
- 進入出征席後自動把焦點／視線放到目前期間與 `派出`，期間選後顯示一個極短的選定回饋（例如 `已選 30 秒`），不新增段落牆。
- `再派` 建立下一趟後沿用上一個期間並在同一 viewport 告知「下一趟已準備」；保留 `派出` 作最後一步。
- 步驟列降為次級導覽，只允許合理可達席位或明確標示「看席位」；履歷回來後保留目前主席位。
- 派出成功顯示短暫、可被 L0 取代的狀態回饋；歸來時若使用者不在主流程，先提示而非無條件 `go('report')`。

### B｜收斂出征面（仍保留主流程）
- 任命→出征→戰報→再派不變，但把出征席做成一個「期間＋派出」單一 action card：期間選擇、已選值、`派出` 緊鄰；`出征詳情` 移到 CTA 後或完全折疊，減少中間掃描。
- `再派` 與任命席 returned 狀態統一導向同一個 ready 出征面；避免任命席的 `去出征` 暗中建立新契約，讓「建立下一趟」只有一個語意入口。
- 可保留步驟列供回看，但主流程以目前席位的單一主 CTA 推進；切席時若有未送出的 NL，顯示非阻塞提醒／保留草稿，不把 NL 移回首屏。

## Open questions｜GPT-6 High／產品

1. 「去出征」與「派出」是否刻意要保留一個確認邊界？若要減一步，產品接受哪一個動作只導航、哪一個動作才是不可逆 commit（且仍維持 `cancel=false`）？
2. 期間是否應永遠沿用上次選值？再派時若期間未變，是否允許直接進入已準備狀態；若有變，回饋要多明確才不違反 L0 ≤2 行？
3. 步驟列是給真人主流程使用，還是主要給 QA／回看使用？「尚無戰報」或「出征中」時，允許任意跳席是否真的有產品需求？
4. 歸來自動 `go('report')` 若使用者已離開出征席，應強制帶回戰報、顯示提示後再留在原席，還是由使用者主動看戰報？
5. `再派`（戰報）與 returned 任命席的 `去出征` 是否應合併成唯一入口？產品要哪一處承擔「建立新 ready 契約」的語意？
6. 派出／期間選擇的最小成功回饋是什麼：L0 更新、短暫 toast，或 CTA 狀態變更？需先定義驗收句，避免加回解釋文案。
